# Рабочие сценарии для агента

> Пошаговые алгоритмы для типовых запросов. Каждый сценарий: что спросить → что сделать → что выдать. Не задавай все вопросы сразу — спрашивай только недостающее, остальное принимай как явные допущения и фиксируй их.

---

## W1. Запуск нового проекта (устав → план)

**Минимум данных:** цель/проблема, спонсор, ограничения (срок, бюджет), ключевые стейкхолдеры, подход (предиктивный/agile/гибрид).

1. **Устав** (`templates/project-charter.md`): цель в формате SMART, критерии успеха, высокоуровневое содержание + **исключения**, вехи, бюджет, риски, РП и его полномочия. Выпиши допущения в журнал допущений.
2. **Реестр стейкхолдеров** (`templates/stakeholder-register.md`): классификация власть/интерес, текущий vs желаемый уровень вовлечения.
3. **Выбор подхода** по `tailoring.md` и `agile-environments.md` §Выбор.
4. **Содержание:** требования → описание содержания → **ИСР** (`templates/wbs.md`) до пакетов работ (8/80, правило 100%).
5. **Расписание:** операции → зависимости → оценки (трёхточечные для неопределённых) → КП (`scripts/pmcalc.js cpm`) → вехи.
6. **Бюджет:** оценки снизу вверх → + резерв на непредвиденные (Σ EMV) → базовый план → + управленческий резерв.
7. **Риски:** идентификация (формула «причина → риск → последствие»), P×I, ответы, владельцы (`templates/risk-register.md`).
8. **Коммуникации и RACI** (`templates/communications-plan.md`, `templates/raci-matrix.md`).
9. **Сборка плана УП** (`templates/project-management-plan.md`), kick-off.

**Выдать:** устав + список следующих артефактов с приоритетом; отдельно — допущения, требующие подтверждения.

## W2. Оценка статуса по EVM

**Нужно:** BAC, PV, EV (или % выполнения), AC на дату статуса.

1. Если дан только % выполнения: EV = % × BAC. Если дан % израсходованного бюджета — это **не** EV.
2. `node scripts/pmcalc.js evm --bac … --pv … --ev … --ac …`
3. Выбери EAC по причине отклонения (`formulas.md` §1): типичные → BAC/CPI; разовые → AC + (BAC − EV); дата жёсткая → CPI×SPI; план неверен → переоценка.
4. Сравни TCPI с CPI: разница > 0,1 — цель BAC нереалистична.
5. Проверь **критический путь**: SPI < 1 не всегда значит сдвиг финиша, если отставание на операциях с резервом.
6. Сформулируй рекомендации: анализ первопричин → корректирующие действия (в пределах полномочий) → запрос на изменение базового плана (если нужно, через 4.6).

**Выдать:** `templates/status-report.md` — таблица показателей, светофор, прогноз, 3–5 действий.

## W3. Обработка запроса на изменение

1. Зафиксировать запрос в журнале изменений (`templates/change-request.md`).
2. Оценить влияние на **все** ограничения: содержание, сроки, стоимость, качество, ресурсы, риски, стейкхолдеров, контракты.
3. Предложить варианты (принять полностью / частично / отложить / отклонить) с последствиями.
4. Передать на решение CCB/спонсору — **РП не одобряет изменения базового плана единолично**, если это не прописано в плане управления изменениями.
5. После решения: обновить план и документы, сообщить стейкхолдерам, реализовать в 4.3, проверить в контроле.

⚠️ Если изменение уже внесено без одобрения — сообщить, оценить влияние, провести через 4.6 задним числом, выяснить первопричину.

## W4. Риск-сессия

1. Проверь, что есть план управления рисками: шкалы P и I, аппетит, пороги. Нет — предложи шкалы (`templates/risk-register.md`).
2. Идентификация: подсказочные списки (PESTLE, TECOP), анализ допущений, SWOT, уроки прошлых проектов. Формулировка: «Из-за … может … что приведёт к …».
3. Качественный анализ: P×I, срочность, приоритет, watch list для низких.
4. Количественный (если оправдано): EMV (`pmcalc.js emv`), Монте-Карло, торнадо.
5. Ответы: стратегия из 5 (для угроз и возможностей), владелец, триггер, запасной план, остаточный и вторичный риски, резерв.
6. Совокупный риск проекта — отдельный вывод в отчёте о рисках.

**Выдать:** реестр рисков + отчёт о рисках (топ-риски, резерв, совокупный риск).

## W5. Аудит проекта на соответствие PMBOK

Пройди по чек-листу, для каждого пункта: ✅ есть / ⚠️ частично / ❌ нет + рекомендация.

| Область | Проверить |
|---|---|
| Интеграция | Устав утверждён спонсором; план УП с базовыми планами; процесс изменений + журнал; реестр уроков ведётся |
| Содержание | Требования + RTM; описание содержания с исключениями; ИСР + словарь; формальная приёмка |
| Расписание | Сетевая модель, КП, базовый план, контроль отклонений |
| Стоимость | Базовый план, резервы разделены, EVM или аналог |
| Качество | Метрики, планы тестирования, аудиты, QC-измерения |
| Ресурсы | RACI (один A), устав команды, календари ресурсов |
| Коммуникации | План коммуникаций, регулярная отчётность |
| Риски | План, реестр с владельцами, ответы **исполняются** (11.6), пересмотры |
| Закупки | Стратегия, критерии выбора, контроль исполнения контрактов |
| Стейкхолдеры | Реестр, матрица вовлечения C/D, план вовлечения |

**Выдать:** таблица результатов + топ-5 рисков процесса управления + план улучшений по приоритету.

## W6. Выбор типа контракта

1. Насколько определено содержание? Стабильны ли требования?
2. Кто лучше управляет риском стоимости? Нужна ли мотивация продавца? Длительность (инфляция)?
3. Выбор по `contracts.md` §«Когда что выбирать». Для incentive-контрактов — расчёт PTA/вознаграждения через `pmcalc.js`.

**Выдать:** рекомендация + обоснование + риски + ключевые условия контракта.

---

## W7. Закрытие проекта / фазы

1. Все результаты приняты (5.5)? Контракты закрыты (12.3)? Претензии урегулированы?
2. Финальный отчёт: цели vs факт (содержание, сроки, стоимость, качество), выгоды, риски и проблемы, уроки.
3. Передача результата в операции, обучение, документация.
4. Обновить АПО: уроки, архив. Высвободить ресурсы. Празднование / признание команды.

**Выдать:** `templates/project-closure-report.md` + `templates/lessons-learned.md`.

---

## W8. Подготовка к PMP

1. Определи слабые области (дай 5–10 вопросов, см. `exam-guide.md`).
2. Для формул — решай вместе с `worked-examples.md`, проверяй `pmcalc.js`.
3. Для ситуационных вопросов — применяй «мышление PMI» (`exam-guide.md` §1).
4. Для ITTO — не зубри списки: пойми, **какой документ где рождается** (`project-documents.md`) и логику потока.

---

## Общие правила ответа
- Называй процесс номером и названием (напр. «6.5 Разработка расписания»), чтобы пользователь мог найти его в PMBOK.
- Разделяй **факты PMBOK** и **практические рекомендации** агента.
- Все расчёты — через `scripts/pmcalc.js` или с показанными формулами; округление — в конце.
- Адаптируй: PMBOK — стандарт, а не методология. Для маленьких проектов сворачивай документы, но не пропускай суть (решение, риск, приёмка).
